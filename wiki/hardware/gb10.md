# GB10 (sm_121) as a kernel target

GB10 is the Grace Blackwell superchip in the DGX Spark: a 20-core Arm CPU and a
Blackwell GPU on one package over a coherent, unified LPDDR5x memory system.
It reports compute capability **12.1 (`sm_121`)**, 48 SMs. This page is what a
kernel author has to hold in mind that differs from datacenter Blackwell
(SM100/SM103); the shared features live in `hw-tma`, `hw-clc`, `hw-mbarrier`,
and `hw-pdl-gdc`.

## Shape of the machine

Measured with `cudaDeviceProp` / `cudaDeviceGetAttribute` on this host (CUDA
13.0, driver 580.126.09):

| Property | Value | How to read it |
|---|---|---|
| Compute capability | 12.1 (`sm_121`) | Not 10.x. `sm_120` is the sibling consumer target; `sm_120f` covers both 12.0 and 12.1. |
| SMs | 48 | ~1/3 of a B300. Grid sizing keyed on an SM100 assumption is wrong here. |
| Max threads / SM | 1536 | Lower than SM100's 2048. Occupancy math changes. |
| Max threads / block | 1024 | |
| Registers / SM | 65536 | Same 64K file as SM100. |
| Shared memory / block (opt-in) | 99 KiB (101376 B) | Default is 48 KiB. SM100 allows 227 KiB. |
| Shared memory / SM | 100 KiB | |
| L2 | 24 MiB | |
| Max cluster size | 8 | 16 fails to launch. |
| Memory | 128 GB LPDDR5x, 256-bit | Coherent and unified with the CPU. |
| Memory bandwidth | 273 GB/s (spec) | ~236 GB/s measured on a 512 MB device-to-device copy. |

The unified memory is not an ordinary discrete-GPU setup: the device reports
`pageableMemoryAccess = 1` and `unifiedAddressing = 1`, so it can read host
pageable memory without a separate staging copy. That is the point of the part
— but it also means the 273 GB/s budget is the *system* budget, roughly 30×
below HBM parts (B200 HBM3e is 8 TB/s). Bandwidth-bound kernels hit the wall long
before compute-bound ones do.

## Compute peaks, for roofline math

The vendor publishes exactly one throughput number: **up to 1 PFLOP FP4 with
2:4 sparsity**. The rest of the ladder below is *derived* by the standard
Blackwell per-precision halving, not published — but both precisions measured
on this host land at ~75% of their derived dense peak, which is mutually
consistent and in line with what large-shape GEMMs reach on other parts.

| Precision | Dense peak | Basis | Measured on this host (2026-10-30) |
|---|---|---|---|
| FP4 (2:4 sparse) | 1000 TFLOPS | vendor headline | — |
| FP4 | 500 TFLOPS | sparse ÷ 2 | — (needs the `sm_121a` path) |
| FP8 | 250 TFLOPS | FP4 ÷ 2 | 184–189 TFLOPS (`torch._scaled_mm`, e4m3, 8192³, bf16 out) |
| BF16 / FP16 | 125 TFLOPS | FP8 ÷ 2 | 93–96 TFLOPS (torch matmul, 8192³); cuBLAS 83–95 |

Roofline consequence: the bf16 ridge point is 125 TFLOPS / 273 GB/s ≈ **460
FLOP/byte** against spec bandwidth (≈530 against the ~235 GB/s a kernel
actually reads at). That is further right than an H100 (~295). Anything that
is not a large GEMM — attention decode, elementwise, reductions, GEMV —
should be treated as bandwidth-bound on this part by default; see
`pattern-memory-bound`.

## Unified memory in practice

`pageableMemoryAccess = 1` and `concurrentManagedAccess = 1`: a kernel can
dereference `malloc`/mmap'd host memory directly over the coherent link. What
each path actually delivers, measured with a grid-stride `float4` read-reduce
kernel over 1 GiB buffers (CUDA events, 10 iterations, 2026-10-30):

| Path | Measured |
|---|---|
| Kernel reads `cudaMalloc` | 235 GB/s |
| Kernel reads `cudaMallocHost` (pinned) | 221 GB/s |
| Kernel reads `malloc` (pageable, zero-copy) | 162 GB/s |
| Kernel reads `cudaMallocManaged` | 161 GB/s |
| `cudaMemcpy` DtoD | 119 GB/s per direction |
| `cudaMemcpy` HtoD (pageable **or** pinned) | 58–59 GB/s |

All rows are **warm-clock** numbers, reproduced across two runs within 2%. The
part downclocks its memory aggressively at idle: the same read kernel launched
from a cold-idle GPU measured **107 GB/s** (cudaMalloc path, ~45% of warm) over
a ~50 ms test, and needed roughly 1–2 s of sustained load before bandwidth
returned to 236 GB/s. Two consequences: short benchmarks from idle understate
this machine by ~2×, and latency-sensitive short kernels launched after an idle
gap run against the downclocked memory. Warm up before measuring anything.

Three rules fall out of that table:

1. **Do not stage with `cudaMemcpy`.** The copy path is the slowest way to
   move bytes on this machine: a kernel reading pageable host memory in place
   gets 162 GB/s where the HtoD copy it would replace gets 58 GB/s — and
   pinning the buffer raises in-place reads to 221 GB/s, within ~6% of device
   memory. The discrete-GPU reflex of "copy in, compute, copy out" costs ~3–4×
   on ingest here.
2. **`cudaMallocManaged` buys nothing over plain `malloc`** for streaming
   reads (161 vs 162 GB/s) — the coherent link, not page migration, is doing
   the work. Reserve it for API compatibility, not performance.
3. **`cudaMalloc` is still the fastest residence** (235 GB/s). For data reused
   across many kernels, placing it there once is still right — but do the
   placement with a kernel or fuse it into the first consumer, not with
   `cudaMemcpy` (119 GB/s per direction DtoD, 58 HtoD).

## What sm_121 is not

The 12.x Blackwell parts do **not** carry the datacenter tensor-core path.
Verified with `ptxas` for `sm_121`/`sm_121a` on this host:

| Instruction family | `sm_121` | `sm_121a` |
|---|---|---|
| `tcgen05.*` (5th-gen MMA, `cta_group`) | rejected | rejected |
| `wgmma.*` | rejected | rejected |
| Tensor Memory (TMEM) | absent | absent |
| `setmaxnreg` | rejected | accepted |
| `mma.sync` f16/bf16/fp8 (`e4m3`/`e5m2`) | accepted | accepted |
| `mma.sync kind::f8f6f4` FP4/FP6 (SASS `QMMA.16832`) | rejected | accepted |

So the SM100 idioms do not port: there is no TMEM to stage accumulators in and
no `tcgen05.mma` to drive them, so `migration-wgmma-to-tcgen05` and the
`hw-tmem` / `hw-tcgen05-mma` contracts stop at the door. Warp-level `mma.sync`
with register accumulators — the Ampere-era model — is what remains.

What *does* carry over from Hopper/Blackwell: TMA (`cp.async.bulk.tensor`),
`mbarrier`, `ldmatrix`/`stmatrix`, `cp.async`, thread-block clusters (up to 8),
CLC (`clusterlaunchcontrol.try_cancel`), PDL (`griddepcontrol`), and
distributed shared memory (`mapa`). A TMA + cluster + warp-specialization
pipeline ports; a TMEM pipeline does not.

## The `sm_121a` split

Some instructions on this part exist **only** under the architecture-specific
target `sm_121a`, not the portable `sm_121`. The sharpest example is FP4/FP6:
the 5th-generation tensor core is present — `ptxas` emits a real
`QMMA.16832.F32.E2M1.E2M1` — but only when the PTX is compiled with
`.target sm_121a`. Compiling the identical source with `-arch=sm_121` fails:

```
error: Feature '.kind::f8f6f4' not supported on .target 'sm_121'
```

Reaching the FP4 path therefore means `nvcc -gencode arch=compute_121a,code=sm_121a`
(or the equivalent in your build system), which trades away forward
compatibility for the tensor-core datapath — the same trade `sm_90a` and
`sm_100a` impose. The same split applies to `setmaxnreg`.

Note that the FP4 fragment layout is not free-handable: the canonical
`mma.sync.aligned.kind::f8f6f4.m16n8k32` operand mapping lives in CUTLASS's
`SM120_16x8x32_TN` (`cute/arch/mma_sm120.hpp`). A hand-rolled operand layout
that ignores it will assemble but not compute what the shape implies — validate
numerically before trusting it.

## DSLs and libraries on sm_121

- **Triton** targets the part directly: Triton 3.7.1 reports
  `GPUTarget(backend='cuda', arch=121, warp_size=32)` and a compiled kernel
  runs correctly (verified on this host, torch 2.13.0+cu130). For elementwise,
  reduction, and attention-prototype work this is the lowest-friction route.
- **PyTorch cu130 wheels** work as-is; the cuBLAS bf16 and `torch._scaled_mm`
  fp8 paths used for the peak measurements above run without special flags.
- **CUTLASS** covers 12.x through the SM120 atoms (`cute/arch/mma_sm120.hpp`,
  blockscaled GEMM builders) — `pr-cutlass-3176` is the upstream trail, and
  the same kernels were integrated downstream in `pr-flashinfer-3152`.
- **Ecosystem bring-up** is traceable in sources: `pr-flashinfer-1608`
  (initial SM103/110/120/121 support), `pr-flashinfer-1610` (CUTLASS fp8 GEMM
  for SM120/121), `pr-sglang-11287` (Spark & Thor enablement),
  `pr-TensorRT-LLM-7937` (GPT-OSS on sm120/sm121), `pr-vllm-33517`
  (`enable_sm120_or_later` CUTLASS guard). The recurring theme in all of them:
  sm_121 rides the **SM120** code paths — version guards written as
  `== sm_120` instead of `>= sm_120 && < sm_130` are the common porting bug.
- **CuTe DSL on sm_121 is unverified here** — no claim either way.

## Verified on this host

The `ptxas` accept/reject table above is a direct test: assemble one instruction
per target and record the result. The full matrix was run on 2026-10-30 (CUDA
13.0 ptxas): `tcgen05.alloc` and `wgmma.fence` reject on both targets;
`cp.async.bulk.tensor.2d` (cluster form), `clusterlaunchcontrol.try_cancel`,
`griddepcontrol`, `mapa`, `mbarrier.init`, `cp.async`, `ldmatrix`/`stmatrix`,
and bf16/e4m3 `mma.sync` all accept on plain `sm_121`; `setmaxnreg` and
`kind::f8f6f4` accept only on `sm_121a` — so every entry in the portability
list above is individually assembled, not inferred from documentation.

```bash
printf '.version 8.8\n.target sm_121\n.address_size 64\n.visible .entry k(){\n  tcgen05.alloc.cta_group::1.sync.aligned.shared::cta.b32 [0], 32;\n  ret;\n}\n' > t.ptx
ptxas -arch=sm_121 t.ptx -o /dev/null      # -> "not supported on .target 'sm_121'"
```

The warp-level path is numerically correct: an `mma.sync.aligned.m16n8k16`
bf16 fragment layout was run on this device against a CPU reference GEMM and
matched on **128 of 128** accumulator elements (worst absolute error 0.0).

```bash
# nvcc -arch=sm_121 mma_bf16.cu -o mma_bf16 && ./mma_bf16
# -> mismatches(>0.05)=0/128 worst_abs_err=0.0000
```

Measured throughput for orientation: a 512 MB device-to-device copy ran at
**236 GB/s**, and a cuBLAS bf16 GEMM (fp32 accumulate) reached **83–95 TFLOPS**
at 4096² / 8192² — consistent with the per-allocator bandwidth table and the
peak ladder in the sections above. The vendor's "up to 1 PFLOP FP4 (sparse)"
headline needs the `sm_121a` path to reach at all.
