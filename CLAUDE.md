# GPU Kernel Optimization Knowledge Base — Schema

A structured knowledge base of GPU kernel optimization, optimized for LLM agent
retrieval, spanning two vendor lanes:

- **NVIDIA** — Blackwell (SM100) and Hopper (SM90). The original and deeper lane.
- **AMD** — CDNA3/CDNA4 (gfx942, gfx950) and RDNA3/RDNA4 (gfx1100, gfx1201).
  RDNA4-first: gfx1201 is the depth target, and every CDNA page states whether
  its content transfers to RDNA4.

## Navigation

### Recommended: use the skill scripts
```bash
python3 scripts/query.py "<keywords>" [--tag X --type Y]
python3 scripts/get_page.py <id-or-path> [--follow-sources]
python3 scripts/grep_wiki.py "<pattern>" [--only wiki]
```
See `SKILL.md` (skill entry point) and `references/examples.md` for query patterns.

### Direct navigation (when skill not available)

1. **Start**: Read `index.md` for curated top-level navigation
2. **By architecture**: Read `queries/by-architecture.md` → choose exact, family-only, or validated-unknown evidence
3. **By problem**: Read `queries/by-problem.md` → find symptom → follow links to pattern pages
4. **By technique**: Read `queries/by-technique.md` → find technique → follow to technique page
5. **By hardware**: Read `queries/by-hardware-feature.md` → find feature → follow to hardware page
6. **By kernel type**: Read `queries/by-kernel-type.md` → find type → follow to kernel pages
7. **By language**: Read `queries/by-language.md` → find DSL → follow to language page
8. **By repo**: Read `queries/by-repo.md` → find repository → see all PRs
9. **Deep dive**: From any wiki page, follow `sources:` IDs to raw source data

## Three-Layer Architecture

### Layer 1: Sources (`sources/`)
Raw data. Each file has YAML frontmatter with a unique `id`.
- `sources/prs/{repo}/PR-{N}.md` — One file per relevant PR
- `sources/contests/{contest}/*.md` — Competition problem definitions, organizer speed-of-light data, and dated leaderboard/results snapshots (no per-submission solutions)
- `sources/docs/*.md` — Official-document and research-paper summaries (`source_category: official-doc` or `paper`); `sources/docs/images/` holds reproduced figure assets
- `sources/blogs/*.md` — Community blog post summaries

### Layer 2: Wiki (`wiki/`)
Synthesized knowledge pages. Cross-referenced by `id`.
- `wiki/hardware/` — Hardware feature pages (tcgen05, TMEM, CLC, TMA, etc.)
- `wiki/techniques/` — Optimization techniques (warp specialization, pipelining, etc.)
- `wiki/patterns/` — Problem → solution diagnosis (low SM util → CLC, etc.)
- `wiki/kernels/` — Kernel case studies (FlashAttention-4, DeepGEMM, etc.)
- `wiki/languages/` — DSL/language guides (CuTe DSL, Triton, CUDA C++, PTX)
- `wiki/migration/` — cross-architecture migration patterns (Hopper → Blackwell, CUDA → HIP, CDNA → RDNA4)

### Layer 3: Queries (`queries/`)
Auto-generated cross-referenced indices. **Do not edit manually** — regenerated by `scripts/generate-indices.py`.

## Controlled Vocabulary

All tags must appear in `data/tags.yaml`. Unknown tags are rejected by the validator.

Alias mappings in `data/aliases.yaml` map canonical terms to known synonyms.

NVIDIA lane:

- `tcgen05` = UMMA = tensor_core_gen05
- `tmem` = tensor-memory = TMEM
- `clc` = Cluster Launch Control = CLC
- `blackwell` = Blackwell family
- `sm100` = B200 = GB200
- `sm103` = B300 = GB300
- `sm90` = Hopper = H100

AMD lane (product → `gfx` mappings are cited to LLVM's AMDGPU processor table
and cross-checked by the validator against
`scripts/pr_policy.py::AMD_PRODUCT_ARCHITECTURE_MAPPINGS`):

- `mfma` = MFMA = matrix core (CDNA)
- `wmma` = WMMA (RDNA)
- `lds` = LDS = Local Data Share
- `cdna3` = CDNA3 family; `gfx942` = MI300X = MI325X
- `cdna4` = CDNA4 family; `gfx950` = MI350X = MI355X
- `rdna4` = RDNA4 family; `gfx1201` = RX 9070 XT = Radeon AI PRO R9700
- `gfx90a` = MI210 = MI250X

## Confidence Rules

- `verified`: official-doc + upstream-code evidence
- `source-reported`: >= 1 authoritative source (paper, official blog, major repo)
- `inferred`: synthesized from multiple sources
- `experimental`: undocumented, PTX tricks, version-sensitive

## Reproducibility Levels

- `concept`: text description only
- `pseudocode`: language-agnostic algorithm
- `snippet`: compilable code fragment
- `runnable`: self-contained buildable example
- `benchmarked`: runnable + perf numbers with env metadata

**Minimum for technique/kernel/language pages**: `snippet`

## Performance Claim Format

```yaml
performance_claims:
  - gpu: B200
    dtype: bf16
    shape: "paper-reported B200 BF16 sweep; exact maximizing shape not stated"
    metric: TFLOPS
    value: 1613
    utilization: "71%"
    source_id: doc-flash-attention-4
    source_locator: "arXiv 2603.05451 abstract and §5"
```

## Tooling

- `scripts/validate.py` — Validates all frontmatter against `data/schemas.yaml`
- `scripts/generate-indices.py` — Regenerates `queries/*.md` from frontmatter
- Setup: no Python package is required; scripts prefer host PyYAML and fall back to the bundled pure-Python implementation. `pip install -r requirements.txt` is optional.
- Run: `python3 scripts/validate.py` then `python3 scripts/generate-indices.py`

## Scope Rules

- **NVIDIA lane is Blackwell-first**: SM100 content is primary. Hopper-only wiki pages require explicit `blackwell_relevance`; source pages preserve upstream evidence and are exempt.
- **AMD lane is CDNA3/CDNA4 + RDNA3/RDNA4-first**, with RDNA4 (gfx1201) as the depth target. Wiki pages whose only AMD targets predate CDNA3 require explicit `amd_relevance`; source pages are exempt. Every CDNA page must state whether its content transfers to RDNA4 — the published AMD corpus is overwhelmingly CDNA and much of it does not port.
- **Kernel-only**: No distributed system topics (DeepEP, DualPipe, EPLB excluded).
- **English canonical**: All content in English.
- **First-class DSLs**: CuTe DSL, CUDA C++, PTX, Triton (NVIDIA lane); HIP C++, Triton-on-ROCm, AMDGCN assembly, Composable Kernel (AMD lane). Others mentioned but no dedicated pages.

## Adding an AMD PR source lane (not yet done)

The AMD lane currently has `sources/docs/`, `sources/blogs/`, and `wiki/` pages
but **no `sources/prs/` coverage**. Adding it is not a content task — it needs
policy work first:

1. `gh auth login`. The PR intake scripts use the GitHub API; unauthenticated
   access is rate-limited to the point of uselessness.
2. Add a `_EXACT_GFX_RE` to `scripts/pr_policy.py` alongside `_EXACT_SM_RE`, and
   AMD device-code signals (`__HIP_DEVICE_COMPILE__`, `__AMDGCN__`,
   `__builtin_amdgcn_*`, `hipLaunchKernelGGL`) to `_DEVICE_CODE_RE` and
   `_ARCHITECTURE_GUARD_LINE_RE`. Then add the AMD families to
   `_EXTRACTION_FAMILY_PREFIXES` and move the AMD products out of
   `AMD_PRODUCT_ARCHITECTURE_MAPPINGS` into `PRODUCT_ARCHITECTURE_MAPPINGS`.
   Until that work is done AMD names deliberately mint no architecture from PR
   prose, because the guard rules cannot corroborate them.
3. Create `candidates/<repo>.yaml` per repo (`ROCm/composable_kernel`,
   `ROCm/aiter`, `ROCm/hipBLASLt`, `triton-lang/triton`) with `searched_at`
   equal to `data/refresh-cutoff.yaml::cutoff_date`.
4. Add one row per repo to the `## Source Repositories (PR coverage)` table in
   `references/primer.md` with the exact on-disk page count — the bijection is
   enforced by `scripts/validate.py::validate_discoverability`.
5. Regenerate `data/pr-architecture-evidence.json` (rows **and**
   `policy_sha256`) and re-run `scripts/verify_pr_architecture_upstream.py`.
